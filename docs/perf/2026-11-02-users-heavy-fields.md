# users 문서 무거운 칸 정리 (2026-11-02, 속도 창)

> 지금은 대표님께 올리지 않는다(머피 브랜딩 11-02). **회원이 500명에 가까워지면** 꺼낸다.
> 코드는 아직 안 바꿨다. 칸을 옮기려면 Firestore 규칙(새 하위 문서·컬렉션) 배포가 같이 필요하다.

## 왜 문제인가

`window._usersAll()`(index.html `_usersAll`)은 users 컬렉션 **전체**를 읽는다(메모리 캐시 5분).
매칭 후보·경매장(`_usersAll(60000)`)·관리자 통계 등이 이것을 부른다. 회원 수에 그대로 비례한다.

측정(손님, 읽기만, 2026-11-02): **252명 · 약 603KB**(JSON 문자 수 기준. 실제 전송은 프로토콜 오버헤드로 이보다 크다).
1인 평균 2.4KB, 중간값 0.9KB, 최대 63KB. 500명이면 약 1.2MB, 1,000명이면 약 2.4MB.

## 바꿀 곳 목록 (줄 번호는 2026-11-02 feat/perf-2 기준, 근사치)

- **bumpDiag**: 쓰기 ~47201–47203(getDoc 내 문서 → setDoc merge). 규칙에 새 경로 추가. 기존 칸 정리는 서버 일회성 스크립트(`FieldValue.delete()`)로.
- **games**: `grep -n "games\." index.html` — 피하기 ~20105–20137·20253, 골프 ~21166–21171, 나머지 게임 같은 꼴. 읽기·쓰기를 `doc(db,'users',uid,'private','games')` 로. 로그인 시 내 문서 읽을 때 같이 읽기 1회 추가.
- **bumpers**: 읽기 ~10291·32266·39026·48042(`_cachedProfile.bumpers`), ~38309·47642(쓰기 전 내 문서), ~37816(matches 쪽 다른 칸이라 무관 — 확인 필요), ~38373(방 주인 문서), 쓰기 ~38332·47658. 서버 `functions/index.js`·`functions/retention.js` 에도 `bumpers` 가 있다 — 같이 확인.
- **artworks**: 저장 ~19005–19009, 내 그림 로드 ~24612, 방문 ~28279·28638·28702·29194·30095, 경매장 ~29381.

## 같이 본 것 — 공개 칸에 든 `fcmTokens`

users 문서는 손님도 전원 읽는다. 그 안에 `fcmTokens`(푸시 토큰, 54명)가 들어 있어 **누구나 남의 푸시 토큰 목록을 받는다**.
토큰만으로 푸시를 보낼 수는 없지만(서버 키 필요) 공개할 이유가 없는 값이다. 옮길 곳: `users/{uid}/private/push` — 쓰는 곳 ~17226·17285·26275·26279, 서버 `functions/index.js`(~231·312)·`functions/retention.js`(~48, `where("fcmTokens","!=",[])` 질의도 바꿔야 함).
속도 숙제와 별개로 개발 창·대표 판단 필요.
